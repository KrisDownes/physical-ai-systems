## Exact interface and scope of the runnable ASID subset

The 2-D Franka end-effector action is bounded ±0.1 m in x and y at 10 Hz; z is fixed, for 20 actions. The source flattens 18 values: 3 end-effector positions, 8 robot joint/gripper positions, and rod position plus quaternion. The rod pose is simulator-derived in simulation; the paper describes depth-camera/color processing on hardware. Observations have author-configured Gaussian noise (standard deviation 0.01, applied across features). The controller is not passed the hidden parameter. The author's `inertia` parameter changes the local position of a lumped mass along the rod, not a scalar inertia: source range ±0.1 m. The saved visualization exposes a blue mass marker; it is **not** a policy image input. Do not claim visual hidden-property inference from the recordings.

The released reward computes squared finite-difference observation sensitivities with shadow simulations and privileged simulator parameters; it is a training/evaluator quantity, not an available deployment sensor. It does not by itself measure balancing success, estimation accuracy, or benefit of interaction. Source resets the randomized model without an explicit `mj_setConst`; whether this affects derived model constants in this MuJoCo version is an unresolved fidelity concern.

Two focused setup attempts are documented: (1) a Python 3.12/dm-robotics 0.8 dependency resolution conflicted with the author's MuJoCo 3.0 pin; an isolated Python 3.9/dm-robotics 0.6 environment resolved it; (2) the author's subprocess workers were blocked by the sandbox's local socket restriction, and the same bounded job ran with approved outside-sandbox execution. Separately, we checked the full pinned repository tree and its archive for the downstream pipeline and checkpoints; neither was present. Fork branches for the fallback were independently resolved but cannot replace missing historical pins or checkpoint. No large dependency migration or custom surrogate was started.

## Transfer route and hypothesis

A second interaction in the same ASID ecosystem is the rod-friction exploration configuration (`configs/asid/friction.yaml`). It could test an adaptation component on a different hidden property, but it is not automatically a held-out task family. Whole-task transfer would require a separate supplied task and task controller, neither supplied for the reported rod-balancing evaluation. First establish an author-supported task outcome comparison.

Observed limitation: prior guided-task predictions did not alter actions. Hypothesis: a fixed history encoder could provide a rod-response estimate that changes grasp selection after interaction. Closest work is ASID's explicit pre-task identification and RMA²'s history encoder. Proposed difference to test is whether the same frozen predictor/context mechanism supports downstream decisions across interactions; no novelty claim. Prediction: on held-out mass positions, matched action histories yield better grasp and lower final tilt than a current-only predictor with identical observation and budget. Disproof: no paired improvement in selection or tilt, or a simple online estimator matches it. Do not run that comparison until the downstream evaluation is credible and available; no our-model comparison has been performed here.
